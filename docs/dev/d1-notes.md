# D1 notes

The database is Cloudflare D1 (SQLite) behind Drizzle (`drizzle-orm/d1`). Read this before you write
raw SQL or a migration. The schema is in `packages/db/src/schema/`, the migrations in
`packages/db/drizzle-d1/`.

## Column types

| Concept                         | Column                                  | Consequence                                                           |
| ------------------------------- | --------------------------------------- | --------------------------------------------------------------------- |
| timestamp                       | `integer({ mode: 'timestamp_ms' })`     | `Date` in TypeScript; raw `sql` sees epoch milliseconds               |
| date (`due_date`, `spent_on`)   | `text`, ISO `YYYY-MM-DD`                | string order is date order                                            |
| JSON                            | `text({ mode: 'json' })`                | no `->>` or `@>`; use `json_extract`                                  |
| boolean                         | `integer({ mode: 'boolean' })`          | raw `sql` compares to 0 or 1                                          |
| uuid with a default             | `text`, `$defaultFn(crypto.randomUUID)` | the default is in the ORM: a raw `INSERT` must supply the value       |
| bigint                          | `integer`                               | safe up to 2^53                                                       |
| decimal (`estimate_points`)     | `real`                                  | a number, not a string; exact decimals are not kept                   |
| default now                     | `(CAST(unixepoch('subsecond') * 1000 AS INTEGER))` |                                                        |

`CHECK` constraints, partial unique indexes and expression indexes (`lower(...)`) work as in Postgres.
A `WHERE` clause of a partial index accepts deterministic expressions only.

`src/schema/auth.ts` is generated by the better-auth CLI (`bun run auth:generate`, config in
`packages/db/auth.cli.ts`). Do not edit it.

## Transactions and locks

- `db.transaction(...)` does not exist on D1. Use `db.batch([...])`, which is atomic, when the statements
  are known up front. Otherwise use one statement (`INSERT ... SELECT`, `UPDATE ... RETURNING`).
  `createWorkspace` shows the pattern (`last_insert_rowid()` inside a batch).
- There are no row locks or advisory locks. The attachment quota is one conditional statement:
  `reserveStorage(db, ...)` inserts only when `used + size <= quota`.
- D1 serializes writers, so no lock-ordering rule applies.

## Raw SQL

- No `now()`: pass a `Date`, or use `unixepoch('subsecond') * 1000`.
- No `ILIKE`: `LIKE` is case-insensitive for ASCII only.
- No `::cast`, `to_char`, `date_trunc` or `extract`.

## D1 limits

- At most 100 bound parameters per statement. Chunk bulk `.values([...])` and `inArray(ids)`.
- 2 MB per row: watch `project_document` content, `note_board` canvas and `agent_run` traces.
- 10 GB per database.
- Foreign keys are always enforced. A migration that rebuilds a table needs
  `PRAGMA defer_foreign_keys = on`.

## Triggers

`drizzle-d1/0001_triggers.sql` holds the triggers that maintain the `revision` counters (see
`revision-engine.md`) and a few invariants. It is hand-written: drizzle-kit never emits triggers, and a
table rebuild drops the triggers of that table. A migration that rebuilds a listed table must re-create them.
`packages/db/src/__tests__/triggers.test.ts` counts and names them after a full migration.

- SQLite triggers are per operation: a logical trigger `x` is `x_i`, `x_u` and `x_d`.
- There are no functions. A bump is an inline `INSERT INTO revision ... SELECT ... WHERE ... ON CONFLICT (scope) DO UPDATE SET rev = rev + 1`.
- `BEFORE` triggers cannot change `NEW`. A default is an `AFTER INSERT` that updates the row.
- There are no deferred triggers. `project_rev_cleanup` is an `AFTER DELETE ON project`, which runs after the
  cascades. Bumps on delete paths are guarded with `EXISTS (project)`.
- Session flags are rows of `trigger_flag`. Insert the row in the same `db.batch` as the writes it governs and
  delete it as the last statement of the batch.
- `RAISE(ABORT, ...)` replaces the Postgres exceptions.

## Migrations

- Generate: `bun run db:generate` writes SQL to `packages/db/drizzle-d1/`. A hand-written migration uses
  `drizzle-kit generate --custom --name=...`.
- Apply locally: `bun run db:migrate:local`. Apply to the deployed database: `bun run db:migrate:remote`
  (the deploy workflow does it before the Workers are deployed). Restores use D1 Time Travel.
- A deployed or `wrangler dev` database is migrated by wrangler only. `migrateD1(db)` in
  `packages/db/src/migrate.ts` is for throwaway test databases. Running both on one database replays the
  baseline and fails on "table already exists", because each tool keeps its own bookkeeping table.
- Seed data is `0002_seed.sql` (the `storage` app setting). The default team role is created with the team.

## Runtime

- `createDb(env.DB)` returns a `Db`. Every function that reads the database takes `db` as its first argument.
  In the api, routes take it from the request context (`shared/context.ts`).
- `@repo/crypto` uses `node:crypto`, so every Worker sets `nodejs_compat`.
- Attachment bytes are in R2. `useR2Bucket(env.BUCKET)` from `@repo/storage` points the package at the bucket
  at the start of each handler.

## Postgres history

`packages/db/legacy-pg/drizzle/` holds the Postgres migrations of the previous deployment. They are never
run. They document the source schema for `scripts/pg-to-d1`, the one-time data migration
(`docs/migration-data-pg-to-d1.md`). `scripts/codemod-sqlite/` is the schema codemod that produced the
SQLite schema. Remove both with the Postgres dependencies (`postgres`, `@electric-sql/pglite`) once the
production data is migrated.
